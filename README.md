# Redis

## Запуск

Для запуска проекта используйте команду `docker compose up -d`

В докере у вас будет развернут кластер Redis на 3-ех нодах, без реплик. 

Также для удобства взаимодействия будет развернут redis-insight, его можно использовать для мониторинга состояния кластера. UI можно найти по адресу `localhost:5540`

Также будет развернут инстанс приложения `leaderboard-app`. Это go-client, который будет использоваться для обслуживания таблицы лидеров. У него есть 3 ручки:

- `leaderboard/get-player` - получение информации об игроке
- `leaderboard/update` - обновление рейтинга игрока
- `leaderboard/get-board` - получение таблицы лидеров

Доступны они будут по адерсу `localhost:8085`

## Хранение данных

Особенность Redis - шардирование по слотам. Слот вычисляется по ключу, а потом сохраняется на нужную ноду согласно распределению:

<img width="488" alt="Снимок экрана 2025-06-08 в 17 44 59" src="https://github.com/user-attachments/assets/d88a00cc-7dd6-4ecd-8016-5ac271178759" />


От приложения по условию требуется максимальная отказоуйчивость - даже если одна из нод откажет и часть слотов соотвественно станет недоступна, остальные слоты должны быть доступны для записи и чтения. Этого можно добиться следующими параметрами в  `redis.conf`:

- `cluster-allow-reads-when-down yes`
- `cluster-require-full-coverage no`

Однако это также накладывает некоторые ограничения на то, как хранить данные.

Например нельзя будет хранить всю таблицу в одном sorted-set. Т.к. расположение этого set-а определяется именно его названием, а не ключом сущности, которая в нем будет сохраняться.

Поэтому для обеспечения максимальной отказоустойчивости мы воспользуемся "шардированным sorted-set":


<img width="1493" alt="Снимок экрана 2025-06-08 в 17 42 59" src="https://github.com/user-attachments/assets/68971403-2df9-410a-a935-114f1ac3ac36" />

Как можно заметить - храниться они будут на разных нодах:

<img width="1408" alt="Снимок экрана 2025-06-08 в 17 45 26" src="https://github.com/user-attachments/assets/9ad31149-21e3-4ad2-816e-a815a3cc3ca1" />

А именно:

- `arena_legends_leaderboard_0` - redis-node-3
- `arena_legends_leaderboard_1` - redis-node-2
- `arena_legends_leaderboard_2` - redis-node-2


### Определение шарды для игрока

Шард будет высчитываться стороне клиента следующим образом:

1. С помощью CLUSTER KEYSLOT считается "потенциальный слот" для игрока(в качестве ключа - id)
2. Берется модуль по количеству шард и конкатенируется с `arena_legends_leaderboard_`

## Послесловие

Подход с шардированием sorted-set в совокупности с соответствующими настройками кластера позволяет обеспечить высокую отказоустойчивость - часть данных остается доступной, однако стоит помнить, что отсутствие другой части данных - может быть критично(геймер в гневе(ибо не нашел себя в таблицы лидеров) - страшная сила. Достаточно вспомнить сериал `The Online Gamer`).
